# Arcus developmental learning and computer-use review

Reviewed September 16, 2026. This is a proposed direction based on the conversation, current code, retained results and primary research. It does not change model weights, rewards, curriculum definitions, permissions, or the accepted roadmap.

**Recommendation: develop Arcus into an agent that can acquire, retain, combine and apply skills across environments. Keep the working simulator as the experimental baseline, qualify its curriculum, then add memory, action-conditioned prediction, deliberate computation, grounded language/perception and controlled computer interaction.** Frontier capability is a research target requiring broad comparative evidence. Neither a child-development analogy nor parameter doubling establishes it, and this review cannot promise a method that learns exactly like a human.

The conversation consistently calls for fresh weights, learning through experience, teamwork, familiar human participation, visible behavior, manual review, approximate size growth, no fixed end date and relocatable services. Recent discussion expands that ambition to persistent experience, thinking and computer interaction. Those later capabilities exceed the intentionally narrow original Baby contract. The optional question about text/images/examples remains a design decision: this proposal preserves fresh weights and does not silently enable pretrained components or imitation learning.

**Scope and evidence.** The review covered the active Baby model, memory, vocabulary, learning, world, curriculum, evaluator and service paths; all 18 core Arcus modules; relevant tests/configuration; the Baby specifications and decision/results records; and selected first-party tool-execution seams. A mechanical inventory records 136 selected text files and 10,100 lines with hashes and Python definition locations in `runs/baby_arcus_development_review/source-inventory.json`. Inventorying a file is not the same as reviewing every line for every possible defect. Dependency environments, vendored projects, private credentials, complete corpora, binary weights and every historical donor run were outside semantic-review scope. This is an architecture/curriculum review, not an exhaustive correctness certification. No model was trained or given computer access during the review.

**What exists today.** Baby has 125,388,431 parameters, a 512-entry structured vocabulary, eight grid actions and nine signals. It uses private recent histories, a shared policy, PPO/GAE, next-visible-observation targets, checkpoints, held-out evaluation and reports. Only two full-size training updates have been accepted in the retained experiment; that is an early diagnostic stage, not a mature learning campaign. The frozen assessment scored switch-delivery 0/200 and clue-search 75/200. The latest unpublished training replay measured KL 0.12942 and clipping fraction 68.64%. These results establish functioning machinery and motivate experiments; they do not demonstrate cooperative mastery or identify a unique cause of poor performance. See [measured results](BABY_ARCUS_RESULTS.md).

**Finding 1 — qualify the curriculum before attributing failure to model size.** In `baby_arcus/lessons.py:28`, practice switch layouts 4 and 5 place the plate immediately next to the door on its approach: `(door_y, plate_y) = (2,2)` and `(4,4)`, before rotation/reflection. The standard holder stands on that plate; the carrier's approach is then occupied. Training layouts 0–3 do not impose this alignment. The practice geometry can require timed handoff/release rather than continuous holding.

A new CPU scripted sweep ran 960 episodes: two families × ten layouts × three difficulties × sixteen seeds. Switch layouts 4/5 scored **0/96**, the other switch layouts **384/384**, and clue-search **480/480**. Static solvability checks passed all 960. This does not prove the practice tasks impossible or measure the learned model. It demonstrates a missing control qualification and a potentially unintroduced dependency. `tests/baby_arcus/test_lessons.py:19` runs its successful scripted control without the actual layout IDs; `lessons.py:64` checks reachability without jointly modeling agent occupancy. Evidence and reproducer: `runs/baby_arcus_development_review/layout-controls.json` and `probes.py`.

The next change should map every template to its prerequisite skills, qualify a successful controller or constructive solution for it, and either teach timed handoff explicitly or choose practice geometry appropriate to the intended prerequisite. Preserve old results; version any changed layouts and evaluation definitions. Do not quietly alter held-out tests to improve a score. This practice issue does not by itself explain the learned checkpoint's failures on the separate held-out layouts.

**Finding 2 — logical training batch and hardware microbatch are currently coupled.** In `baby_arcus/learner.py:51`, every part of size `microbatch` zeroes gradients and performs an optimizer step. There is no gradient accumulation. With 1,116 transitions, two passes and microbatch eight, there are 280 optimizer steps. Therefore microbatch is an optimization choice, not just a memory setting. Separate the logical optimizer batch from the hardware microbatch and compare one factor at a time: logical batch, learning rate, PPO passes and prediction weight. Record behavior and final-policy/epoch-level divergence as well as the existing pre-step means. The measured clipping fraction is a diagnostic, not sufficient evidence for an automatic threshold or a particular fix.

**Finding 3 — current memory is recent context, not lifelong memory.** `baby_arcus/memory.py:42` drops old complete frames; `services/inference.py:50` starts fresh histories for each episode. A 512-token budget is not 512 world steps. Sampled scripted histories after twenty steps retained roughly 9–14 switch-task frames; this is context capacity, not demonstrated remembering. Add memory tasks that cannot be solved from the latest observation, then compare longer context, compressed recurrent memory and explicit retrieval. Later episodic memories need source/episode/time/identity metadata, correction and expiration, and isolation from protected test episodes. A stored observation and a fact learned in weights are different things; measure both.

**Finding 4 — outcome prediction is not yet a model of candidate actions.** In `baby_arcus/model.py:54`, the action and prediction heads use the same pre-action hidden state. The current executed action is not an argument to that predictor, while `experience.py` supplies the next observation as its target. It can learn outcomes averaged over the current policy, but cannot directly compare consequences of alternative actions. Add a separate dynamics branch conditioned on permitted history plus action/signal, leaving the actor's input before the action unchanged. Evaluate calibration and unseen action consequences before using multistep imagined trajectories. In a two-agent world, represent uncertainty about the teammate; never hand an actor its partner's private observations or future action.

World-model learning is a supported research direction: DreamerV3 learns environment dynamics and improves behavior using imagined trajectories. Its evidence supports investigating that mechanism, not assuming Arcus already has it or that it guarantees human-like learning. Dreamer also acts through its learned actor rather than requiring online lookahead at every step. [Hafner et al., Nature 2025](https://www.nature.com/articles/s41586-025-08744-2).

**Finding 5 — deliberate computation needs a trained mechanism and a fair test.** Baby currently performs one trunk evaluation for an action. MoD layer skipping is not an internal planning loop. Prototype either recurrent internal processing or short action-conditioned lookahead after its prerequisites work. Compare one, two and four internal steps with training budgets, inference cost and latency recorded. Test against a control spending similar compute another way. A think button or a generated explanation would not establish improved reasoning. Recurrent-depth language-model research demonstrates a possible mechanism, but its reported 3.5B-parameter/800B-token experiment is not evidence of the same benefit in this 125M grid policy. [Geiping et al.](https://arxiv.org/abs/2502.05171).

**Finding 6 — interaction with you needs grounding and a new input contract.** The current vocabulary accepts only agents `a`/`b`, fixed roles/goals and named signals; the dashboard is GET-only. Stable human identities, teaching/play-only sessions and feedback attribution must exist in the environment and learning contracts as well as the UI. Familiarity should be measured by remembering permitted preferences or coordinating successfully, without claiming emotional attachment. Shared-play scores must remain separate from autonomous scores.

Fresh weights can remain the experiment's origin while the range of experience expands. Reading, labeled perception, language grounding or demonstrations would each need a defined objective, data provenance and held-out checks. The original specs explicitly exclude imitation, general language, persistent notebooks and imagination-based RL. These are decisions to version, not features to imply are already present. If reward-and-prediction-only learning remains mandatory, natural-language teaching and broad desktop competence become a more constrained research program; they are not supplied by watching a few unlabeled screens.

**Finding 7 — growth is a later capacity experiment.** The current operator expands experts, not attention width or layer depth, and does not migrate optimizer state. A static estimate for four→eight Baby experts is about 125.39M→244.94M total parameters, not exactly 250M. This is arithmetic, not a measured Baby growth run. In `arcus/moe.py:104`, capacity per expert is `ceil(capacity_factor * tokens / experts)`; adding experts can shrink existing buffers and drop tokens even when clones are dormant. Growth tests must preserve task heads, vocabulary and useful behavior; measure overflow, actual new-expert learning and memory/runtime; and compare with simply training the parent longer. A plateau can come from a curriculum, exploration or optimization problem.

Keep the newer cautious Baby growth contract. The historical text result 56.58→60.03→15.32 perplexity demonstrates expansion followed by further learning, but its loader changed and old checkpoints had validation-document exposure. It cannot establish pure growth advantage or the entire 85B ladder. `docs/RESULTS.md` itself also records incoherent text generation. Reconcile broad historical claims and stale README/spec status headers without deleting the measurements.

Model scale, data and training compute must be budgeted together. Chinchilla supports that point for the language-model setting it studied; it is not an RL rule that maps each parameter to twenty simulation steps. Local experiments can qualify mechanisms and measure throughput. Frontier-scale resource feasibility remains open until a concrete architecture/data target is costed. [Hoffmann et al.](https://arxiv.org/abs/2203.15556).

**The developmental learning loop should become:** perceive the environment, update private working memory, retrieve relevant permitted experience, predict consequences, spend a bounded amount of computation choosing, propose a typed action, observe its verified result, then learn from eligible records between sessions. Candidate checkpoints should pass retention and transfer tests before becoming the active policy. Old experience may support a separately designed prediction/retention objective; it must not be fed into vanilla on-policy PPO as if freshly collected. Continual learning needs both old-skill retention and the ability to acquire new skills; these can fail independently. [Dohare et al., Nature 2024](https://www.nature.com/articles/s41586-024-07711-7).

| Proposed learning stage | Example experience | Evidence needed to advance |
|---|---|---|
| Action consequences | Reach a target, move around a wall, pick up and place an object | Success on unseen layouts; failure types understood; retention of previous actions |
| Remembering | See an object, leave it out of view, encounter a distraction, return | Improvement over memory-disabled controls at varied delays and unseen locations |
| Predicting and choosing | Try different actions in comparable visible situations | Calibrated action-conditioned predictions; no hidden-state leakage; planning benefit on held-out tasks |
| Cooperation | Hold, wait, hand off, communicate private information | Message removal/shuffling, role swaps and partner changes affect the learned policy as expected |
| Human participation | You and your wife join distinct teaching/play sessions | Identity/session handling, bounded feedback, and later autonomous retention verified |
| Computer classroom | Click a named object, type a symbol, remember a tab, save a practice file | Verified app/file state, novel layouts, instruction grounding and recovery from mistakes |
| Broader transfer | Combine known skills in an unfamiliar application/workflow | Autonomous completion, learning efficiency, retention and resource costs against named baselines |

These stages are skill gates, not developmental ages or a fixed calendar. Preserve teamwork from the beginning through simple complementary tasks, while allowing short prerequisite lessons. A persistent world should be a controlled option; resettable lessons and isolated held-out worlds remain necessary for interpretable tests.

**How computer interaction should work.** Start with local resettable browser microapps and practice files. Use structured DOM/accessibility observations as the first bridge if helpful, then add an explicitly trained visual encoder and evaluate screenshots separately. Success from privileged DOM data cannot be reported as screenshot understanding. Ground text instructions and typed action arguments; the current fixed grid symbols cannot express arbitrary filenames or documents.

Keep a trusted execution broker separate from the learned policy. It receives typed proposals, checks target freshness and the session's allowed apps/folders/actions, executes within that scope, and records outcomes. Reuse request IDs, receipts, deadlines and replay evidence. Practice first in a disposable desktop/VM with fixture accounts/files. A Windows host helper or controlled desktop bridge belongs outside the Linux GPU worker; container deployment alone cannot provide Windows interaction. After isolated tasks pass, allow bounded real-computer sessions with an operator stop control and clear boundaries for external sends, purchases, account changes or destructive operations. Routine permitted reversible actions need not ask for confirmation every click.

Desktop evaluation should inspect actual resulting application/file state, include failed-action recovery and changed layouts, and report assistance separately. OSWorld provides a relevant execution-based benchmark pattern. Pin its version and keep benchmark tasks out of training; this review does not claim Arcus has run it. [OSWorld project](https://osworld-v1.xlang.ai/).

The LLM supervisor can review logs and suggest approved curriculum changes. It should not silently supply Arcus's answers during an evaluation. Report Arcus alone, Arcus with its own memory/planning, and human/LLM-assisted systems separately. The viewer can display actions, retrieved memories, predicted outcomes and timing; these are inspectable records, not direct access to subjective thoughts.

**Decisions still to settle:** whether experience may include explicit text/image learning and demonstrations while retaining fresh weights; whether the first computer interface is structured UI or pixels; and what capabilities, named external baselines, evaluation conditions and resource budget will define the word “frontier” for this project. No dates, intelligence doublings or locally feasible final model size are promised by this roadmap.
